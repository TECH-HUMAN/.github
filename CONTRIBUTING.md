# Colaboração na organização Tech Human

Estas orientações ajudam colaboradores a localizar contexto e registrar mudanças com clareza. As instruções específicas de cada repositório, seus contratos e gates continuam sendo a referência para executar e validar o trabalho.

## Antes de alterar

- Leia o README e as instruções locais. Identifique a branch padrão, a fonte canônica e as frentes em andamento.
- Diferencie repositório de aplicação, export de plataforma, fonte editorial e distribuidor público. Altere conteúdo na fonte indicada.
- Use somente os acessos e ambientes autorizados. Valores de segredos ficam no gerenciador de ambiente, nunca em commits, exemplos, logs ou issues.

## Issues, PRs e revisões

- Abra uma issue quando houver problema, decisão ou trabalho que precise ser acompanhado. Descreva contexto, resultado esperado e critérios de conclusão.
- Atribua a issue e o PR ao responsável real pelo trabalho. Relacione o PR à issue pertinente e mantenha o estado fiel ao que foi entregue.
- Use uma branch com escopo claro; para trabalho com Codex, a convenção é `codex/<escopo>`.
- No PR, explique problema, mudança e validação, incluindo limitações observadas. Siga o template e os checks locais.
- Peça revisão a uma pessoa com contexto e acesso. Autoria, atribuição e aprovação são papéis distintos; uma atribuição não substitui revisão.
- Faça commits e revisões que correspondam a trabalho efetivo. Registre a origem de contribuições assistidas por agentes conforme a convenção local.

## Documentação e publicação

Um README útil informa objetivo, público, estado verificável, configuração, estrutura, integrações, verificações e fontes de referência. Use o [modelo adaptável](docs/README-TEMPLATE.md) sem inventar comandos, licença, deploy, prontidão ou capacidades ausentes.

Informações de clientes, dados pessoais e estratégia interna permanecem nos espaços privados autorizados. Revise também arquivos anexos e histórico antes de compartilhar externamente. Relate exposição de credenciais pelo canal privado do responsável pelo repositório; não inclua o segredo em issue pública.

Merge, build, deploy e disponibilidade real são etapas diferentes. Preserve os gates e a rotina de publicação de cada projeto; documentação atualizada não atesta lançamento de produto.
